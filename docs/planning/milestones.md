# milestones

this order is provisional. the first implementation should test the kernel through real domain libraries instead of polishing syntax around an unproven engine.

## M-1: semantic prototype

define typed values, requests, rules, dependency recording, structured diagnostics, and an in-memory query interface.

status: complete.

evidence: the rust prototype has a typed pure step machine, exact-interface rule selection over the current interface subset, cycle diagnostics, dependency recording, instance-owned graph identities, exact in-memory reuse for completed pure applications, structured diagnostics, and an in-memory query surface. it constructs versioned, domain-separated pure-computation keys over separate stable rule identity and cache-invalidating rule revision (0023). action capability requirements propagate canonically through completed pure dependencies, and actual capability use is retained as dependency edges and exposed through the query interface.

persistent graph and cache storage, equality-based change pruning, and invalidation explanations belong to the incremental and caching work in M-2. operational support for `Observation`, `Mutation`, and `Opaque` belongs to the milestones that exercise those effects. neither is required to reopen this semantic prototype milestone.

## M-2: action prototype

add content-addressed blobs and trees, sandboxed local actions, caching, and explanations for cache hits and invalidation.

current evidence: blobs and trees are content addressed, with tree identity preserving file executability and symlink targets; the engine accesses them through an injectable pith-owned content-store interface. the in-memory and filesystem adapters implement that interface. the filesystem adapter atomically publishes blob bytes and canonical tree manifests, verifies identity on reads, and preserves content across store instances. pure steps can request deferred blob materialization, and action planning produces a validated, inspectable contract with a stable digest. pure computation keys use the stable rule identity and cache-invalidating revision from decision 0023. every scheduler run supplies an action policy, named allow and deny decisions are retained in provenance, and denial prevents executor invocation. the engine materializes only declared executable and input content for an executor, imports captured output bytes and trees into the engine store, and gives action rules engine-owned content identities. executors still return structured reports, and the engine retains successful and rejected reports in provenance. every computation that leaves `Pending` is published to a pith-owned engine-state interface, and a pure request that this engine instance has not evaluated is answered from the durable reusable index after its recorded dependency set revalidates: the completed attempt loads into a fresh arena node carrying the durable identity of the attempt it came from, so later computations depend on that attempt rather than a duplicate. equality-based change pruning exists for this path — a dependency recomputed to a canonically equal result leaves its consumers reusable — but not yet as a general propagation mechanism. a sqlite adapter stores that state as normalized relations, and a result computed by one process is hydrated by another after the writer has exited. the two adapters are held to each other by a generated conformance suite rather than by a shared encoding. reopening the database marks attempts left `Pending` by an interrupted owner as cancelled, so a reader finds a consistent graph rather than one waiting on a process that will not return, and finds it recorded as work that was stopped rather than work that failed. invalidation explanations are built as a chain over the recorded dependency graph: `EngineStateStore::explain_invalidation` walks the latest completed attempt's recorded reuse reason, following the single dependency it names, and both adapters share the walk through a common `AttemptLookup`-driven builder. the live arena exposes the same chain through `EngineQuery::explain_invalidation`, and the cross-adapter conformance suite compares the explanation for every pure key alongside the existing reuse and history reads. a first-party executor exists: `pith-executor-local` stages declared inputs and the executable into a per-action scratch root, runs the child with only the declared environment, captures declared outputs back from that root, and refuses a spec whose network policy or platform it cannot honor rather than running it under a weaker contract. its confinement is partial — the child gets `no_new_privs` but not yet the landlock ruleset or the seccomp allowlist decision 0028 describes — so it reports `AccessVerification::Unverified`, which is what it actually installed. independent work evaluates concurrently: a rule body declares that a batch of requests do not depend on one another with a single fan-out step, `run_many` drives one chain per root request, and the scheduler overlaps their actions while each chain stays on the synchronous step machine (0029). the overlap is measured rather than assumed — a test holds three actions at a barrier that only releases once all three have arrived. a run is cancellable: `run_cancellable` polls a caller-supplied signal at scheduling boundaries, and work stopped that way is recorded `Cancelled` — a terminal state distinct from `Failed` in the arena, in the durable record, and in the cross-adapter conformance suite — so a reader can tell a computation that cannot work from one that never got to run. the local executor kills its child when a cancelled action's future drops. that overlap is bounded: a chain that stops for an action queues the request and the driver starts it only while fewer than `Engine::action_concurrency` actions are running, so a fan-out of a thousand requests holds a thousand chains but plans, materializes, and spawns a bounded number of them. the landlock ruleset is installed (decision 0030 confines the scratch root, declared outputs, and declared toolchain closure); the seccomp allowlist remains, as do timeouts and cancelling part of a run rather than all of it. action caching is no longer disabled: decision 0031 splits action identity into a request-side key that indexes a completed attempt and an execution-side admission test that decides whether the recorded attempt may be served to this run, so an unchanged action is answered from the reusable index within one engine instance and across instances. a completed pure attempt holding an action dependency now enters the reusable index (decision 0033). its action edge is revalidated by re-selecting the recorded interface against this run's action rules, calling `plan()` on the recorded inputs, and comparing the key that derives to the one the attempt was recorded under; the current run's policy authorizes the contract that plan produced, and 0031's admission test decides whether the recorded execution may be served. a key that derives differently does not make the consumer dirty on its own — the engine reads the latest reusable attempt under the new key and compares its result to the recorded one, which is the equality-based pruning across the effect boundary 0031 left open, at the edge a build most wants it at. revalidation is run-scoped for this reason: `ReuseContext` carries the policy and executor identity from the driver to the reuse path, and `Engine::evaluate_pure` has neither, so it declines any attempt carrying an action edge, matching its refusal to take an effectful step. `ReuseReason::EffectfulDependency` is no longer produced by either the arena or the publication validator, and an action edge whose target is reusable stops blocking reuse.

## M-3: first build library

build a small project with at least two toolchains, generated input, tests, and fine-grained rebuilds. all build concepts use public library APIs.

current evidence: one toolchain runs, declared as a closure of host paths and confined by landlock. `crates/pith-executor-local/tests/real_toolchain.rs` compiles a C source file to an object file through `Engine::run` and the local executor — the engine plans the contract, materializes the source, the executor execves the declared compiler path with a landlock ruleset over the scratch root and the declared toolchain closure, captures the object, and content-addresses it, with no change to the engine for a tool it did not author. the toolchain enters the contract as a declared closure of host paths (decision 0030), obtained from `nix path-info --recursive` over the compiler's store path. that discovery lives in `crates/pith-executor-local/tests/support`, not in a library: 0030 gives it to the build library this milestone opens, and until that exists the tests stand in for it. two runs of the same compile in different scratch roots produce byte-identical objects, so this compile is deterministic in the sense 0014 keeps separate from confinement.

running the compiler under the ruleset found two more things. **a toolchain needs somewhere to write.** the assembler creates temporaries, and confined to a scratch root it cannot reach `/tmp`. the executor now creates a `tmp` directory beside the working directory and exports `TMPDIR` naming it, so the temporary directory is part of the sandbox the executor builds rather than something every action has to remember to declare. **`ldd` does not answer the closure question.** it picks a loader from `PATH`, so inside a nix devshell it resolves a distribution binary against nix's glibc and names libraries that binary will never open; asking the loader named in the binary's own `PT_INTERP`, via `LD_TRACE_LOADED_OBJECTS`, is the answer that matches what the kernel opens. the nix store path avoids the question entirely, which is why 0030 makes it the supported one.

the slice that first ran the compiler found three things, each of which changed what the build library has to be. **a toolchain is not an executable** — resolved by 0030: `ActionSpec::executable` is now a host path and a declared `toolchain` closure carries the paths the action may read, so landlock confines the toolchain the action actually used rather than a convention. **the seccomp allowlist in 0028 is a sixth of what a compiler needs**, and the missing part is structural rather than incidental — process creation, because the driver is a supervisor; the landlock ruleset is installed but the seccomp layer is not, so `AccessVerification` reports `Observed` (path confinement enforced, syscall confinement still absent) rather than `Prevented`. both layers' measurements are recorded in 0028's unresolved section. **fine-grained rebuild needed an action identity**, which is decision 0031: the second run of an unchanged compile plans the same contract, derives the same `ActionComputationKey`, and is served the first attempt.

action results are cached (0031). the key is the request half of action identity: the selected rule's identity and revision, the requested interface, the request inputs, and the digest of the contract planned from them. the execution half is knowable only after an executor has run, so it becomes an admission test when reuse is considered — the recorded execution must come from the executor and platform this run would use, its `AccessVerification` must meet the engine's floor, its recorded dependencies must revalidate, and the content it produced must still be in the store. any of those failing is a miss, and the action runs. `Executor` gained `identity`, so the engine can ask who is about to run before it reads the index, and both engine-state adapters carry a reusable action index that the cross-adapter conformance suite compares alongside the pure one. the consumer of an action stays out of the index and records `EffectfulDependency`: a pure key does not carry the identity of the action rule that will be selected, so a pure result recorded before that rule was revised could otherwise be served after it. what reuse skips is the execution, which is where the cost sits. `ActionCachingDisabled` now means `Engine::set_action_caching(false)`, and the determinism check runs under it, because a served result is identical for having the same bytes and says nothing about what the tool would produce a second time.

the first build library exists: `crates/xylem`, the first crate to take a botanical name (docs/foundation/name.md). it owns the toolchain closure discovery 0030 assigns to it — `Toolchain::discover` is the public API the test support in `pith-executor-local` stood in for — and declares compile and link actions over the nominal types 0026 names, which Phase 0 of the calculus made inhabitable. a toolchain is a `Value::Nominal` request input so dispatch distinguishes compiles over different toolchains, and `CSource`, `Object`, and `Executable` are distinct nominal content types so two content-producing rules no longer collapse to `() -> Blob` and collide as `E-1102`. the two-source build fixture in `crates/xylem/tests/two_source_build.rs` is the first time the repository asserts U-5's fine-grained invalidation: touching `a.c` recompiles `a.o` and re-links, but the `b.o` compile is served from the reusable action index, so the second build adds two action computations rather than three. the fixture now builds over a sqlite state database beside its filesystem content store, which lets it assert what decision 0033 added: a second build of unchanged sources reports `Reused` at the root and plans no action, and a fresh engine opened over the same root after the first is dropped reports `Hydrated` and allocates no computation beneath the root. before 0033 every target of a build sat above an action and so re-ran on every build, surviving no process boundary. linking is fixed-arity two for now; variadic linking needs a list or tree-valued content variant (0026) and is its own decision. header dependencies are declared by hand in the fixture; a `-MMD` depfile pass is the real answer and is follow-up work, which the installed landlock layer makes safe to start from — a wrong declaration fails loudly rather than silently.

## M-4: package and environment libraries

add package identity, basic constraints, lock data, binary reuse, and a reproducible development environment.

## M-5: Linux system library

compose files, users, a service, and boot configuration into an immutable Linux artifact.

## M-6: deployment library

observe one machine, derive a plan, apply it, confirm the result, and return to an earlier realization. secrets use references resolved at the target.

## M-7: broader execution

only after the vertical slice works: remote execution, additional operating systems, multi-machine placement, continuous reconciliation, and richer transition protocols.
